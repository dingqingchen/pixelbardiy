# MCU 本地动画与显示所有权

## 1. PC 发目标，MCU 生成过程

PC 已经知道下一句歌词、下一页指标或新主题的最终图案，只需要发送这个目标点阵及动画编号。MCU 保存旧画面和新画面，在主循环中根据时间生成中间帧；不用 PC 每隔十几毫秒发送一整幅图片。

这解决了早期方案的两类问题：USB 传输速度不足时上推只有一帧过渡；旧字幕动画只处理中央区域，左右图案固定不动，看起来像撕裂。新固件增加真正覆盖 **256 × 32 全屏** 的动画，客户端按已验证的固件 SHA 选择相应编号。

## 2. 代码放在哪里

显示 MCU 应用镜像长 57,252 字节，映射到 `0x08002000..0x0800FFA3`。不能简单在旧处理函数后拼接补丁：后面已有 OTA 等代码；直接加长镜像也受到原接收器上限约束。

本方案将原厂背景位图**无损压缩**，通过解码帮助函数保持原来的背景输出，在 `0x0800AF24..0x0800D724` 范围内重新安排压缩资源及扩展代码。字体和 OTA 等不在目标替换范围内的区域保持原布局。当前换色固件在这块回收区域还剩 **1,032 字节**；这不是整颗 MCU 剩余 Flash/RAM，也不是可以随意扩大镜像的许可。

构建时逐字节检查改动区间，离线执行原厂 30 个主题场景和 16 个字体用例作回归。[空间回收基线](../legacy-python/firmware-lab/validate_bitmap_space.py)、[扩展构建](../legacy-python/firmware-lab/validate_codec.py)和[当前汇编](../halo-studio-dotnet/firmware-color/codec_color_thumb.s)均保留。

## 3. RAM 布局

地址采用左闭右开区间。地址只适用于已核对的这一版固件，不应套到其他型号。

| 区域 | 地址 | 大小 | 用途 |
| --- | --- | --- | --- |
| RX | `0x20001340..0x20001358` | 24 B | 接收帧状态 |
| EX | `0x20001358..0x200013B8` | 96 B | 解码器、帧 CRC、动画及待提交 RGB 状态 |
| OLD | `0x200013B8..0x200017B8` | 1024 B | 动画开始时的旧画面快照 |
| LEASE | `0x200017C0..0x200017E0` | 32 B | 租约魔数、SID、时钟、存活时间及会话记录 |
| FB | `0x200017F0..0x20001BF0` | 1024 B | 供原厂屏幕刷新函数读取的当前画面 |
| STAGE | `0x20001BF0..0x20001FF0` | 1024 B | 解码后的新目标帧 |

这些范围互不重叠，但部分空间原本属于原厂图像上传工作区。合法性依赖**独占租约期间暂停会使用它的原厂路径**，并非永久闲置 RAM。新版换色只使用 EX 内已有的两个空闲字，不为每个像素增加 RGB 内存，也不另开动画帧队列。

接收期间只写 STAGE；目标 CRC 通过后才允许更新颜色。直接显示则复制目标到 FB 并刷新；动画则先把当前 FB 保存到 OLD，在每一步从 OLD 与 STAGE 合成 FB。完成后发布完整 STAGE。下一帧开始前会处理未完成动画的状态，避免将某个中间画面误用为已提交的差分基准。

## 4. 时间推进与具体效果

原厂定时调用处增加租约时钟计数；**定时中断只计时，不绘图**。主循环的 `anim_tick` 计算 `elapsed / interval`，相同步号不重画，必要时跳过已错过的步号。间隔参数允许 8–64 ms；常用 16 ms。32 步的名义时长约 512 ms，但它不保证实机恒定 62.5 fps，实际调度还受原厂主循环和显示总线影响。

| 编号 | 效果 | 实现 |
| --- | --- | --- |
| 0 | 直接显示 | 完整目标提交后刷新 |
| 1 / 2 | 旧字幕上推 / 横向揭幕 | 保留旧协议的中央字幕区域，装饰区保持目标图案 |
| 3 | 整屏上推 | 32 步，全部 256 列共同位移 |
| 4 | 整屏横向揭幕 | 32 步，每步约揭开 8 列 |
| 5 | 字符雨 | MCU 程序化生成字符流星与尾迹，160 步后显露目标图案 |
| 6 | 中心展开 | 32 步，由中央向两侧展开，每侧每步 4 列 |
| 7 | 像素溶解 | 8×4 阈值模板遍布全屏，32 步逐渐改用新画面的像素 |

全屏上推的像素模型（步数 `s=0..32`）：

```text
if y + s < 32: output(x,y) = old(x,y+s)
else:          output(x,y) = target(x,y+s-32)
```

汇编把每列 4 个页字节组装成 32 位列，通过移位拼接完成上推。横向揭幕按 `x < 8*s` 选择新列；中心展开按 `128-4*s <= x < 128+4*s` 选择新列。输出四个页字节后调用原厂刷新包装，不改变屏幕总线时序。

溶解不是上传随机噪声视频。令 `a=x%8`、`b=y%4`，阈值为 `4*(a XOR (a>>1)) + (b XOR (b>>1))`；阈值小于步号就采用目标像素，否则保留旧像素。实现将 4 位列掩码纵向重复，不需要额外的全屏阈值数组。

字符雨同样由 MCU 根据列号和步号生成小字符、不同落点与尾迹，后段显露 PC 发送的标题/图案。PC 无须传送 160 张字符雨图片。整屏共色的硬件使“明暗”主要通过点阵密度、空隙和尾迹构造，不能对不同字符设置独立 RGB 渐变。

## 5. 独占、心跳与退出恢复

PC 侧使用进程间显示锁；MCU 侧使用 SID 与租约校验，并对原厂绘图、调度、上传和部分接收路径加门控。PC 锁只能约束遵守它的程序，不能拦住所有外部软件；真正保护共享显示 RAM 的是 MCU 门控。

客户端约每 500 ms 续租，正常数据往来也刷新活跃时间。MCU 在约 2000 个计时 tick 无有效活跃后释放租约；用户实测已确认停心跳会恢复原厂时钟。恢复在主循环执行，观察到画面变化还包括原厂调度延迟，不能把超时常数直接当作肉眼恢复时间保证。

释放时会失效当前会话、清理上传/调度状态、取消动画并恢复原厂显示路径；迟到或格式错误的 HPL2 包不能掉进普通资源上传逻辑。PC 正常退出还会恢复进入前的颜色，并多次检查原厂时钟状态稳定，避免重新显示缓存的旧监控文字。

当前固件在帧 CRC 通过时调用原厂颜色输出函数；不修改保存的配置 RGB。退出或超时后恢复原厂配置颜色。主题间换色不释放租约，因此旧画面能直接进入新过场，不再夹一帧原厂时钟。

## 6. 验证能证明什么

[validate_color.py](../halo-studio-dotnet/firmware-color/validate_color.py)执行真实 Thumb 指令，并使用独立像素模型核对动画 6/7 的各步全屏像素、旧动画、错误包、CRC、帧号回绕、释放/超时和原厂色值编码。只模拟显示总线、物理 DMA 等外设边界；不是完整芯片或完整开机仿真。

实机已经验证全屏同步移动、字符雨、连续换色、正常退出和停止心跳恢复。日常显示检查没有 Flash 调用。**初次安装或升级固件仍会写存储，不能与 RAM 直绘混为一谈**；完整掉电恢复/死机救砖能力见[固件说明](FIRMWARE.md)。
