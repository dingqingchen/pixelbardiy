# 屏幕颜色：协议与实机结果

## 2.6.1 官方色表与自由取色核对（2026-10-14）

从本机 **EDIFIER TempoHub 1.3.0** 的 Halo PixelBar 像素屏颜色页及其产品 41222 的主题色缓存核对了 30 个预设。官方名称未标注，所以 HaloStudio 自拟中文名并统一加「官方」前缀；按 RGB 色相排序、白色置后，`official_index` 保留官方界面原来的阅读顺序。颜色来自像素屏页面，不是其他设备或氛围灯的色表。

静态检查的是已安装 EXE（SHA256 `688e245659bc90e4589ce91f65f34ef6bdc682bb7f7533dcdcbf777b9f664369`）中的 Python 字节码，没有执行提取出的官方模块，没有进程注入，也没有把静态分析说成 USB 抓包。核对链路如下：

1. `SoundBoxPixelColorView.__update_default_color_layout` 将同一个预设 HEX 用作色块外观与选中值；`ColorSelectView.set_selected_color` 转为 `QColor`。
2. 调色板拖动从色盘图像 `pixelColor(x,y)` 取值；输入 HEX 则直接构造 `QColor`，RGB 编辑也使用其三个通道。色盘的渐变/游标定位不是设备色彩校正。
3. `__color_view_selected` 取 `red()/green()/blue()`，`SoundBoxPixelColorModel.send_value_select` 原样交给 `pixel_screen_set([3, r, g, b])`。
4. `ECDriver.pixel_screen_set` 发送 EF 命令，不修改 RGB。此像素屏链路没有调用软件中另存的 `ColorTransMap`，没有发现伽马、白点或色彩矩阵转换。官方缓存的 `#AARRGGBB` 中 `FF` 是 alpha，去掉后就是 RGB，不可误当红色。

因此，「官方 RGB」入口和这 30 个官方预设都原值发送，包括白色 `#FFFFFF`。**官方预览与硬件颜色准确一致尚未经逐色实屏验证**；原值直传不等于光学标定。以前的 G1 浅绿、P2 淡粉、土黄和本机白色减蓝仍保留在主题／校准组，不会自动被替换。

同一个 HEX 可以有不同来源：`theme_colors` 保留原 RGB；新增 `theme_official_colors` 为每个主题保存官方直传标记。旧配置缺少该字段时沿用原行为。「白色」应用 `screen_white_blue`；「官方霜白」绕过它。切回校准色或恢复主题原色清除该主题的官方标记。演示场景携带各自来源，避免采用当前主界面主题的补偿规则。氛围灯、亮度、电流、MCU 镜像均未改变。

外部 `palettes/pixelbar.json` 的 `colors` 仍是已有校准色元数据，新增 `official_colors` 是独立数组，允许与已有组使用相同 HEX。热加载先完整校验两个组，失败时保留原表。自定义未知 RGB 不做插值或未经验证的转换。

## 柔和快捷色与主题原色

快捷色采用近似观感的色相顺序：**柔红 → 土黄 → 浅绿 → 离子蓝 → 猫咪蓝 → 淡粉 → 白色**。排序依据 `preview` 的观感，不能按设备 `input` 排序，否则已校准的主题色会错位；无彩色白放在末尾。外部 JSON 的条目顺序就是界面顺序，`quick: true` 的条目显示为快捷色。

纯绿、纯蓝分别由已核对的 G1 浅绿与离子蓝替代，六套主题默认色全部纳入快捷选项，同色不重复。新增柔红设备值 `#D8321C`，降低红通道并少量混入绿蓝；预览目标为 `#EA8C88`，**尚未实屏核对**，不能作为已校准样本或任意 RGB 映射依据。旧纯色仍保留为隐藏元数据，以识别已有自定义颜色；不会自动改写用户已保存的选择。既有土黄、浅绿、淡粉及白色校准保持原值。本次只调整外部色表，不更新固件。

## 2.5：浅绿与淡粉实屏校准（2026-10-14）

G1 `#60FF30`、G2 `#90FF48`、G3 `#B0FF60`：用户反馈 G1 较绿，G2 开始变蓝，G3 为蓝绿色。P1 `#FF3040`、P2 `#FF6048`、P3 `#FF9060`：用户反馈 P2 接近淡粉，P1 更像紫色；P3 没有明确结论。雷达使用 G1、桃兔使用 P2，并加入调色板快捷色。土黄 `#FF6000` 与已校准白 `#FFFF90` 原样保留。

这是离散查表，不将少数样本外推成完整 RGB 转换。输入依旧是设备驱动值，预览颜色分别为近似浅绿 `#A4EBAC` 与淡粉 `#F2B3C8`；已保存的自定义主题颜色优先，恢复主题原色可采用新默认。

新版 MCU 接受 15 字节 BEGIN 元数据，在原 12 字节之后追加 RGB；只有目标帧解码和 CRC 全部通过才调用原厂颜色输出函数。帧与换色使用同一个 SID，无须 RELEASE 或 EF，避免原厂时钟插入。颜色保留在 RAM；不改保存的颜色、亮度、电流和输出时序。释放或超时后重用原厂配置颜色。3 字节追加不增加帧头的 USB 包数。

2026-10-13，Halo PixelBar 1.3.7 / 已验证 HPL2 字符雨固件，Python 与 C# 客户端交叉测试。结果来自本机使用者目视确认，没有使用色度计，不能据此给出 sRGB 覆盖率、准确白点或可分辨颜色总数。

## 2.4.2：预览观感和设备输入分离

`palettes/pixelbar.json` 在启动或点击「重新加载色表」时读取，包含 `input`（保留的设备输入）、`preview`（电脑上近似示意）、`name`、`observation` 和 `quick`。色卡、六个主题缩略图、实时预览和演示预览共用此表。预览 RGB 是根据用户的文字观感选择的示意色，不是测量出来的色度坐标，不声称精确匹配。

- 琥珀仍发送 `(255,96,0)`；预览改为 `#C7A34A` 土黄。切换到新版本不会改变其实屏效果。
- 桃兔预览 `#BC93EF`，猫咪预览 `#89A1F0`，雷达预览 `#9EC5F1`，只修改电脑上的示意。
- 白色仍使用独立的 `screen_white_blue`；本机 144 对应发送 `#FFFF90`、预览目标白 `#FFFFFF`。没有将减蓝比例重复应用。
- 快捷色按已核对的色相命名。任意颜色入口改为「设备 RGB…」，未知值明确标为未校准；不做未经验证的插值。
- 现有主题 `color`、用户 `theme_colors`、演示输入、氛围灯输入及 USB 传输逻辑不改变。`preview` 绝不可用于发包。
- 格式错误的色表原子拒绝，保留已加载数据；初次启动没有有效色表时使用原 RGB 参考图并记录 `palette-warning.txt`，仍可手动选择设备 RGB。

## 为什么同一组数字在两块屏幕上不同

已核实的 MCU 软件链路是：`+LCD+SET` 的 R/G/B → `0x0800998C` → `0x080098FA`，逐通道计算 `floor(channel × brightness / 100)`，以 GRB 顺序写入 `0x20002A64`；`0x08009804` 将 14 组三字节编码为高低脉冲值。GRB 是输出字节顺序，不等于把逻辑红绿互换。USB 主控 `0x0600A8CC–0x0600A8E0` 直接复制三个缓存色值进入该命令。

`halo-controller/firmware-lab/validate_color_path.py` 离线执行原厂 1.3.7 和当前字符雨固件中的真实 ARM 指令，分别验证 3,865 组输入（各单通道 0–255、五组混合色，亮度 0/5/10/50/100），并检查每个输出字节的全部脉冲位。两包 `0x08009804–0x080099D5` 代码相同，所有结果符合上述公式，没有伽马表或混色矩阵。报告为 `validation/color-path.json`。仿真不访问设备，也不验证实际电气时序或光学表现。

电脑调色板通常用非线性 sRGB 编码，LED 接收的数值更接近驱动强度。直接复制中间值会使各通道的光强比例偏离电脑显示。例如 sRGB 的 G=96 对应约 0.117 线性光强，即 8 位约 30；直接向线性驱动发送 96 则约为 0.376，绿色相对红色太多，橙色容易趋黄。屏幕透光层、LED 三原色和各通道效率还会引入额外差异。此机白色需将 B 从 255 降为 144，与蓝色相对过强相符；这仍只是一个白点观感，不能证明整个蓝通道都是同一比例。

这里的“缺少 sRGB 转换 + 通道不平衡”是与代码和观感相符的模型；不是已经测得的整屏光学响应。现有证据不支持靠交换 RGB 顺序解决：三个纯色已经分别核对过。

## 完整任意色调色板的后续模型

推荐分为两层：已核对色卡使用精确查表（当前已实现）；自由调色使用独立设备配置中的通道曲线 / 白点 / 必要时三原色矩阵（待实屏标定）。UI 显示目标 sRGB，设备值隐藏在其后，旧主题和手动 RGB 保留原值模式以防重复转换。

可用于下一轮有限测试的初始模型为：

```
x = sRGB / 255
linear(x) = x / 12.92                  (x <= 0.04045)
            ((x + 0.055) / 1.055)^2.4 (其余)
device ≈ round(255 × linear(x) × gain)
gain 初始猜测为 (1, 1, 144/255)
```

这个公式没有接入日常发送：144/255 只是基于线性通道假设的候选值。一个白点和“偏蓝 / 偏紫”的描述不能唯一决定三条响应曲线，更不能确定三原色色域。需用少量红绿、红蓝、绿蓝混色与灰阶对照确定中间点，或用色度计测量后拟合单调 LUT；不同亮度需要检查一致性。超出实屏色域的目标应限制到可显示范围，并标出近似，而不是提高通道电流硬追颜色。琥珀已认可的旧设备值需要作为保留色固定下来。

原理参考：[ICC sRGB 编码定义](https://registry.color.org/rgb-registry/srgb)、[Adafruit LED gamma 与橙色趋黄示例](https://learn.adafruit.com/led-tricks-gamma-correction?view=all)。

## 2.4.1 本机白色校正

再次进行有限时间减蓝对照，R/G 固定为 255，仅降低 B：W0=255、W1=224、W2=192、W3=160、W4=128、W5=96、W6=64。用户确认 W3/W4 比较接近白色，W2 偏蓝，W5 偏绿；W6 没有得到明确观感确认。随后取 W3/W4 中间值 B=144（`#FFFF90`）单独播放 WHITE 144，用户确认「这档白色合适」，作为本机保存值。该确认是肉眼观感，不是色度计测量或标准色域认证。

「主题与屏幕 → 主题配色 → 白色偏蓝校正」可调整蓝色分量，255 表示关闭补偿。本机值写入 `screen_white_blue`，便携包不包含该用户设置，其他设备默认保持 255。主题、预览和快捷色继续使用逻辑白色 `#FFFFFF`，只在连接与提交显示帧时映射实际发送 RGB；不会作用于其他颜色、灰色、氛围灯或原厂退出恢复色。减蓝不提高原白色任何通道的数值，也未改动亮度上限、电流或 PWM 时序。

## 协议能说明什么

- 256×32 画面是 1-bit 点阵掩码；整屏共用 RGB，不能为不同像素分别着色。
- EF 屏幕颜色命令含 R、G、B 三个字节，每通道数值范围 0–255。EE 回读对测试值均返回原数值；它读的是 USB 主控缓存，不能证明显示 MCU 已经执行，更不能证明实际发光颜色准确。
- 已检查的显示 MCU 路径将三通道按亮度缩放，转换为 GRB/PWM 输出；没有发现仅允许蓝、紫等少数预设色的枚举限制。此结论不等于 1677 万种颜色都可准确显示。
- USB 主控通过延迟任务转发 `BLT+LCD+SET#`；HPL2 独占期间会拦截原厂显示命令。客户端换色会释放租约、设置颜色、等待原厂时钟和缓存状态稳定后重新接管，合并中途的新选择，只画最新目标。

当前证据可排除「屏幕只支持紫蓝」，但尚不能精确测得面板光学特性和通道响应。颜色校准没有提高电流或改变 PWM；2.5 固件更新用于消除换色释放显示权导致的闪钟，沿用原厂颜色输出函数。

## 测试范围

颜色对照使用有限时间文字与小色块，结束恢复原厂显示。驱动电流和亮度上限保持不变；安装 2.5 MCU 扩展只需一次固件更新，日常换色、过场与图形更新仅操作 RAM。实机安装记录与离线报告分开保存。
