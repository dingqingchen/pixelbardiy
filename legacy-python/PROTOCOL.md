# Halo PixelBar USB / HPL2 协议

本页描述已验证的 1.3.7 显示 MCU 补丁与电脑端实现。旧版原厂资源/文字仍在 `halo/device.py`，新版普通显示只发送 RAM 像素。

## USB 外层

VID `0x2D99` / PID `0xA106`，HID interface 4，usage page `0xFF14` / usage 1；一次 report 为 64 字节。

```text
输出：2E AA TYPE CMD LEN_BE16 PAYLOAD CHECKSUM ZERO_PADDING
输入：2F BB EC   CMD LEN_BE16 PAYLOAD CHECKSUM ZERO_PADDING
```

CHECKSUM 是从第二字节到负载末尾的累加模 256。负载不超过 57 字节。普通设备类型是 `ED`，MCU 更新路径使用已实测的 `EC`。响应逐项校验前缀、命令、长度和校验和。不是裸串口报文。

| 命令 | 用途 |
| --- | --- |
| `66` | 查询硬件音量/链路状态；本项目不改音量 |
| `6A` / `6B` | 查询/设定氛围灯 |
| `EE` / `EF` | 查询/设定屏幕颜色和原厂模式 |
| `C6` | 查询 USB 主控回报版本 |
| `17` | 原厂资源传输；新版在保留数据序号上封装 HPL2 |
| `E7` / `E8` | 旧版原厂文字查询/设定 |
| `10` / `11` | 独立更新器使用的通知/请求驱动更新数据 |

原厂 `17` 资源上传会写 Flash 并显示上传状态。新版 `RamDisplay._write()` 有硬性命令白名单，普通帧只能发送 `17` 的 HPL2 封装，不能调用资源 START/END、文字、音量或升级路径。

## HPL2 数据包

`17` 负载：`00 02 FF FF` 后接：

```text
"HPL2" op:u8 sid:be32 frame:be16 index:u8 length:u8 data[length]
```

SID 非零，每次接管随机生成；单片数据最多 37 字节。当前系统只允许一个在途请求、一张正在发送的画面和一个可替换的最新目标。

| op | 内容 |
| --- | --- |
| 1 | ACQUIRE，获取显示租约 |
| 2 | HEARTBEAT，维持租约 |
| 3 | 原始帧 BEGIN |
| 4 | 原始帧 DATA：1024 字节像素 + CRC16 |
| 5 | RELEASE，释放并恢复原厂时钟 |
| 6 | 编码帧 BEGIN，带 12 字节编码元数据 |
| 7 | 编码帧 DATA |

获取、心跳、数据片回复 `00 03 FF FF`；完成/释放回复 `00 05`。这些是 USB 桥返回状态，不能作为 MCU 逐像素读回证据。

## 点阵、压缩和差分

显示尺寸为 256 × 32。1024 字节按四个 8 像素高页排列；像素 `(x,y)` 位于 `data[(y//8)*256+x]` 的 bit `y%8`。

op 6 的数据：

```text
codec:u8 animation:u8 interval:u8 reserved=0:u8
encoded_length:be16 base_id:be16 base_crc:be16 target_crc:be16
```

- codec 0：原始 1024 字节。
- codec 1：无损 RLE。token 低 7 位加 1 得到长度；高位 1 表示重复紧接的一个字节，高位 0 表示随后跟对应长度的原文。
- codec 2：目标与最后已完成帧 XOR，再用 RLE。基帧号和 CRC 必须匹配；已取消但未提交的帧不能作为基底。

CRC 使用 CRC-CCITT（`binascii.crc_hqx(data,0)`）。解码恰好产生 1024 字节，并验证顺序、长度、边界、基底、最终 CRC 后才发布可见帧。每 64 帧强制独立帧；电脑端选择字节最少的编码。新目标可在当前片 ACK 后取消未完成画面；若最后一片已在途，则等待其完成。错误不盲目重放片段。

## 本地动画与内存

animation 0 直接显示，1 向上推入，2 横向揭幕。interval 允许 8–64 ms，默认 16 ms。24 阶段只移动 x=38..237、y=4..27，主题装饰保持。收到一个目标后 MCU 的主循环服务动画，不需要电脑发送每个中间帧。其他整页或装饰动画可由 PC 生成。

| RAM 区间（结束地址不含） | 用途 |
| --- | --- |
| `20001340..20001358` | 原始接收状态 |
| `20001358..200013B8` | 编码/动画状态，96 字节 |
| `200013B8..200017B8` | 动画旧画面，1024 字节 |
| `200017C0..200017E0` | SID、租约和控制状态 |
| `200017F0..20001BF0` | 可见帧，1024 字节 |
| `20001BF0..20001FF0` | 暂存帧，1024 字节 |

这些工作区复用原厂上传缓冲，只在租约有效时独占。原厂资源、文字、绘制调度和设置保存均在 MCU 检查租约；OTA/关机等必要控制保持原路由，并先释放。PC 发现 TempoHub 等竞争进程时不接管；退出/新版旧版切换用同一个锁和串行停止屏障。

## 心跳、退出与主题换色

PC 每约 500 ms 发送心跳。MCU 独立计时约 2000 tick 后释放，旧 SID 不能再次夺回显示。半帧不会提交。主程序正常退出先处理在途响应，再 RELEASE；不确定时等待租约超时，然后切原厂时钟并要求 2.5 秒稳定状态，避免 USB 主控重播旧监控文字。

主题颜色属于硬件设置，必须先释放再改。换色流程为 RELEASE → EF 颜色/时钟 → EE 校验 → 新 SID ACQUIRE，采用非阻塞交接，180 ms 合并快速连续选择。等待期间继续检测媒体，新接管后只发送最新歌词/目标，避免主题切换堆积旧歌词。

## MCU 代码空间和更新

1.3.7 MCU 应用为 57,252 字节，映射 `0x08002000..0x0800FFA4`，初始 SP `0x20003B58`。启动区和 USB 主控不在该段里。

十幅原厂背景位于 `0x0800AF24..0x0800D724`，共 10,240 字节。无损压缩背景、目录与小型解码器保留原显示，把回收空间用于 RAM 接收、租约、编码和动画；不是把新代码追加到应用末尾或扩展 Flash。

当前核心 588 字节，session 1232 字节，codec 1008 字节，OTA 兼容模块 92 字节；剩余回收空间 1684 字节。补丁钩子、向量、保留边界和字节范围由离线构建校验，详见 `firmware/hpl2-codec/candidate-review.json`。

旧 HPL2 原型把 OTA DATA 首字节的高位误判为废弃 START 标记。因此从旧版升级时按文件内容选择最多 55 字节的无损边界，确保包首字节低于 `80`。新补丁将标记检查限定于 START。两个高位图案区被 XOR `80` 编码并在原显示入口还原；相关字形和 30 个原主题样例验证一致。整个候选 1057 包逐字节发送一致，未插入或删改传输字节。

原厂完整 PC_137 包为 `13 字节头 + MCU + 厂商名为 BLE 的 USB/音频主控段 + 50 字节零尾部`。本项目的固定 MIX 通知复现原厂包头，但只响应 MCU 数据请求，遇到下一主控段请求停止，不发送主控内容。

## 证据与限制

ARM/Thumb 反汇编、实际机器码仿真和真实 USB 测试是不同层级的证据。仿真使用 Unicorn 2.1.3，模拟 Flash 写入底层，执行真实 parser、dispatcher、原厂复制/刷新代码与补丁。USB 桥转发有静态证据，未做 Jieli 指令级仿真。设备实测完成重启、图形、压缩、两类动画、退出与断心跳恢复；没有进行完整 Flash 读回或擦写次数测量。

安装记录仅作为本机对已验证设备的显式授权，不是厂商签名、固件认证或 MCU 读回。主控版本 `1.3.7` 在修改前后相同。启动区独立并不能保证损坏应用后还能刷入；独立救砖入口未确认。参见 [更新和恢复](docs/FIRMWARE.md) 与 [验证记录](docs/VALIDATION.md)。
